# RouterForge — единая дизайн-система и модернизация интерфейса

**Мастер-план разработки · UI Unification v1.0 · 22 октября 2026**

**Проект:** `Fifth-Ace/routerforge` · **ветка:** `dev` · **зафиксированная база аудита:** `4e966c2dc658639d8fe2f07a54de544ef72e78b4`

**Статус:** план утверждён в рамках текущей задачи; P0 Foundation подготовлен к безопасной доставке, дальнейшие этапы не опубликованы.

> **Два обязательных эталона:** визуальный язык блоков, цветов и состояний — NFQWS Manager (скриншот 1); читаемость, заголовки и типографика — Главная RouterForge (скриншот 2). «Настройки» (скриншот 3) перерабатываются функционально и композиционно. Под «статистикой» в настройках подразумевается учёт установок и необязательная телеметрия проекта, а не локальная телеметрия железа в боковой панели.

## 1. Цель, результат и границы

**Цель:** все страницы Core и все собственные менеджеры RouterForge должны выглядеть частями одного приложения: одинаковые смысловые цвета, контраст, типографическая иерархия, размеры контролов, статусные обозначения, плотность, сетки, отступы, логика заголовков и доступность. Разнородные HTML/CSS-реализации остаются технически независимыми, но соблюдают единый визуальный контракт.

**Что получаем:**

- одно визуальное соглашение для главной, системных страниц и устанавливаемых модулей;
- компактные «Настройки» с четырьмя логическими категориями: **Система**, **Интерфейс**, **Журналы**, **Безопасность**;
- статистика RouterForge внутри **Системы**: базовый учёт, переключатель дополнительной телеметрии, состояние регистрации и HTTPS-сервера;
- одинаковые шаблоны для page header, карточек показателей, секций, форм, таблиц, вкладок, действий и уведомлений;
- ограничение CSS-переопределений и точечная интеграция в каждый модуль без переписывания работы служб;
- воспроизводимая матрица визуальных и функциональных проверок с однозначными условиями PASS/FAIL.

**В проект НЕ входят:** изменения поведения DNS/NFQWS/firewall/CrowdSec/Port Access, API и сохранённых настроек; публикация Stable или Beta; развёртывание на VPS; касание production-роутеров; переделка внешних приложений, исходный интерфейс которых RouterForge не контролирует; перенос или изменение локальной телеметрии оборудования в боковой панели. Внешние UI получают только единую оболочку, ссылку, описание и проверку встроенного отображения; их собственный дизайн остаётся авторским.

## 3. Каноническая палитра и дизайн-токены

Опираться на `routerforge-shell.css` и проверенную палитру NFQWS; избегать второй системы глобальных значений. Ниже — семантика и целевые значения по текущему коду.

| Токен | Цвет / источник | Назначение |
|---|---|---|
| `--rf-bg` | `#0b0d10` | фон приложения |
| `--rf-surface` | `#12151a` | фон секций и карточек |
| `--rf-surface-2` | `#171b21` | вторичная поверхность, контролы |
| `--rf-hover` | `#1d2229` | наведение, выделенная строка |
| `--rf-text` | `#f5f7fa` | основной текст |
| `--rf-muted` | `#8d98a4` | пояснения и метаданные |
| `--rf-border` | `#29313a` | обычные границы |
| `--rf-border-strong` | `#36414d` | выделенные границы |
| `--rf-accent` | `#38bdf8` | ссылки, выделение и primary-контроли; зависит от существующей темы |
| `--good` / `--warn` / `--bad` | `#2ea043` / `#d29922` / `#f85149` | успех / внимание / ошибка; в менеджерах через локальные алиасы |

**Важно:** зелёный — не новый основной цвет интерфейса; это семантика успешно работающего состояния. Синий accent остаётся системным для ссылок/выделения, если пользовательская тема не задаёт иной допустимый оттенок.

**Размеры/ритм (целевой UI-contract):** 4/8/12/16/20/24 px; межкарточный gap 12 px; контроль 34–36 px высотой; радиус карточки 8 px, кнопки 5–6 px; граница 1 px; плотность compact/default/comfortable реализуется через переменные, не копированием целых тем. Ни один компонент не должен задавать фиксированную высоту для длинного текста.

**Типографика:** шрифт `Inter` → `Segoe UI Variable Text` → `Segoe UI` → `sans-serif`; моноширинный только для версий, SHA, путей, логов и кодовых значений. Иерархия: заголовок страницы 23–26 px / 650–700; крупная секция 16–19 px / 650; заголовок карточки 13–15 px / 650; обычный текст 13–14 px / 1.45; помощник 11–12 px. Минимальный читабельный размер: 11 px для UI-подписей; значения 9–10 px только для ограниченных моно-бейджей при проверенном контрасте.

### 3.1. Семантика статусов

Статусы **НЕ взаимозаменяемы**:

| Измерение | Возможные состояния | Визуальное отображение |
|---|---|---|
| Установка | INSTALLED / NOT INSTALLED | нейтральная карточка / отсутствует |
| Служба | RUNNING / STOPPED / UNKNOWN | зелёный / красный / серый |
| Включённость | ON / OFF | зелёный / серый |
| Здоровье проверки | PASS / WARN / FAIL | зелёный / жёлтый / красный |
| Обновление | UPDATE / CURRENT | жёлтый / нейтральный |
| Выполнение | BUSY / SUCCESS / ERROR | индикатор загрузки / зелёный / красный |

Не писать «READY» вместо RUNNING, если сервис только установлен; обновление не должно превращать работающий процесс в «ошибку». Статусы маркируются текстом и цветом (не только цветом).

### 3.2. Компонентный набор (контракт)

- **PageHeader** — breadcrumb, H1, описание 1–2 строки, действия/статус справа; мобильный перенос.
- **SectionPanel** — заголовок и содержимое, минимум декоративной вложенности.
- **MetricCard** — короткое название, значение, пояснение; одинаковые отступы и метрики.
- **ActionCard / ActionBar** — чёткое действие и объяснение, не скрывать опасные действия среди обычных.
- **StatusChip** — текстовый статус и семантический цвет; один дизайн для модулей.
- **SegmentedTabs** — управление разделами/подразделами; aria-current/tabindex, поддержка клавиатуры.
- **SettingRow** — label/helper/control; значение выравнивается по правому краю без гигантских пустых колонок.
- **DataTable / EmptyState / Notice / ConfirmDialog** — общие отступы, контраст, состояния загрузки/ошибки.

Существующие компоненты повторно используем там, где их контракт совпадает. На P0 добавляем неймспейсные **CSS-примитивы**, а не меняем поведение живых страниц.

## 4. Страница «Настройки»: утверждённая архитектура

**Приоритет P1.** Убираем текущую композицию «узкий левый системный столбец + длинная правая простыня». Вместо этого — единая ширина страницы и компактный системный summary сверху с понятной группировкой.

**Проектируемый макет:**

1. Заголовок `Настройки` + короткое пояснение. Справа статус Core при необходимости.
2. Горизонтальная системная сводка: версия, статус, uptime, DNS/обнаружение (только уже имеющиеся данные).
3. Переключаемые группы в одной строке: **Система · Интерфейс · Журналы · Безопасность**. Состояние вкладки сохраняется в URL/hash или локальном UI-состоянии; не менять серверные настройки при переключении.
4. Только активная группа раскрывается в основной области: без пустой высокой колонки; на мобильных группы идут адаптивным списком.
5. Кнопки «Сохранить» локальны своей секции; опасные операции требуют прежних подтверждений.

### 4.1. Система

В одной логической секции две компактные подгруппы:

**«Сведения о системе»** — фактическая версия, онлайн-статус, uptime, основные DNS, discovery, используемая память процесса (при наличии). Не дублировать всю Главную.

**«Статистика RouterForge»** — учёт установок (постоянный и обезличенный), дополнительная статистика модулей (по умолчанию включена, отключаемая), статус защищённого сервера и подтверждение регистрации. Пояснение: случайный ID установки, отсутствие передачи личных данных/конфигураций, перечень версии Core/архитектуры/официальных модулей с версиями. **Не добавлять CPU, RAM, температуру или локальные журналы в отправляемые сведения.** Точный текст должен соответствовать действующему протоколу.

Не размещать прямую ссылку на закрытую админ-панель Collector в пользовательских настройках роутера.

### 4.2. Интерфейс

Уровень интерфейса, масштаб, тема, язык, режим обновления SSE/polling, порог **локального** предупреждения по температуре. Последний параметр НЕ является внешней телеметрией; оставляется для локального UI.

### 4.3. Журналы

Хранилище, действующий путь, лимит размера, число архивов, отдельное сохранение. Пути и ограничения безопасности те же, что были; UI не подменяет файловую логику.

### 4.4. Безопасность

Аутентификация, сессии и существующие переключатели/подтверждения. Текущие авторизационные сценарии, CSRF/origin, формы и модальные окна не переписываются ради дизайна.

### 4.5. Поведение при отсутствии данных

Пока не загрузился Core/API — статус «Загрузка»; при недоступном endpoint — «Нет данных» или «Недоступно» без фальшивого зелёного. При сохранении — busy; при ошибке — читаемое сообщение рядом с нужным контролом. Проверять включение/отключение телеметрии и подтверждение регистрации без ложного сброса состояния.

## 6. Подробный план выполнения

### P0 — Foundation & Contract (первый выполняемый пакет)

**P0A. Инвентаризация:** закрепить текущие CSS и Svelte/HTML entrypoints, источники палитры, список компонентов, карту владельцев интерфейса и исключения. Артефакт — этот мастер-план и `docs/UI_DESIGN_SYSTEM.md`.

**P0B. Неймспейсные UI-примитивы:** добавить `components/core/frontend/src/routerforge-ui-primitives.css`, загружать после существующего `routerforge-shell.css`; только новые классы `.rfu-*` и переменные `--rfu-*`, без глобальных стилистических переопределений. Артефакт — работающий `dev` CSS-contract, который не меняет текущий экран до явного использования.

**P0C. Статическая проверка:** контроль исходного SHA, whitelist paths, файлы и суммы, Svelte import, уникальные классы, `npm run check` в CI, отсутствие изменений release/assets, workflow jobs на точном SHA.

**PASS:** новый CSS импортируется, Core собирается, текущие страницы не изменены визуально, CI и rolling Dev успешны. **FAIL:** любой unexpected path, неактуальная база, конфликт импортов, compile failure.

### P1 — Settings Redesign (первый видимый этап)

- **P1A** — сохранить точные preimage файлы `settings/+page.svelte`, текущие настройки UI, telemetry/auth/logging handlers; зафиксировать тестовые сценарии и старые значения.
- **P1B** — вывести компактный системный summary без постоянной пустой левой колонки.
- **P1C** — интерфейс 4 групп с клавиатурным управлением; дефолт «Система».
- **P1D** — перенести блок «Статистика RouterForge» внутрь «Системы», убрать дубли пояснений, сохранить работающий endpoint телеметрии.
- **P1E** — журналирование, UI, безопасность поместить в соответствующие группы; не изменять запросы, пути или методы.
- **P1F** — test locale RU/EN, light/dark, 320–1920 px, off/online, авторизация и сохранение.

**PASS:** не исчез ни один текущий контрол; клики, сохранения и API совпадают; нет прокрутки пустой левой колонки, широких мёртвых участков и горизонтального overflow.

### P2 — Core Pages

- **P2A** Главная: закрепить эталон H1/H2, status, metric rows.
- **P2B** Мониторинг: карточки, таблицы, подсказки, состояние отсутствия данных.
- **P2C** DNS: страницы серверов, маршрутизации, traffic/tools, действия.
- **P2D** Управление: дерево, редактор/терминал, модальные подтверждения.

Каждая из P2A–P2D — отдельный маленький коммит и Dev CI, со скриншотным сравнением «до/после» и функциональной проверкой.

### P3 — Integrations & App Center

- **P3A** Сетевые инструменты: формы и результаты.
- **P3B** Интеграции: карточки модулей и внешних UI, менеджерные workspace.
- **P3C** Центр приложений: установка/обновление/удаление/ошибки, список пакетов.
- **P3D** Основная оболочка: боковая колонка, заголовок, кнопки, компактность, ссылки.

**PASS:** названия модулей не перепутаны с внешними integration targets; deep links, iframe checks, opkg status, update badges работают прежним образом.

### P4 — RouterForge Managers

- **P4A** NFQWS: документированный образец token mapping, минимальная доводка.
- **P4B** Antiscan: сократить локальные style overrides, привести layout.
- **P4C** Port Access: аудит CSS-каскада и точечная унификация, по одному экрану/функции за коммит.
- **P4D** CrowdSec: перевести палитру и контролы на семантические алиасы.

**PASS:** каждое функциональное действие и опасная операция остаются под старым механизмом подтверждения, статусы правдивы, плотность совпадает с эталонами.

### P5 — Themes, Locale, Accessibility, Responsive

- Light/dark и кастомные переменные не хардкодятся во вторичных модулях, если Core предоставляет токен.
- RU/EN: локализованы новые тексты, длина надписей не ломает сетку.
- Клавиатура: видимый focus, tab-order, переключение вкладок, Escape модальных окон, отсутствие клавиатурных ловушек в контейнерах.
- Контраст: обычный текст ≥4.5:1, крупный текст ≥3:1; не полагаться исключительно на цвет.
- Размеры: 320 / 390 / 768 / 1024 / 1440 / 1920 px; zoom 100/125/150%; компьютер, телефон, 2K/4K без фиксированной высоты.
- Динамические данные: loading, empty, error, no-permissions, installed/update/running/stopped и длинные версии/пути.
- Движение: `prefers-reduced-motion`, отсутствие бессмысленных анимаций.

### P6 — Hardware Acceptance & Release Readiness

- CI на точном SHA для каждого шага; никаких workflows `full_release/publish_beta`.
- Проверка Dev только на явно разрешённом **DSTest ARM64**, `NFQUEUE_300` остаётся нетронутой, рабочие и production-роутеры не используются.
- Golden-path: открыть каждую страницу, сравнить скриншоты, проверить доступ к модулям/вкладкам/настройкам, read-only и допустимые action workflows.
- Проверить изменение, повторную загрузку, сохранение UI-предпочтений, переключение RU/EN, масштаб, темы.
- Отдельный review по доступности и регрессиям.
- Только после письменного разрешения готовить отдельный Beta или Stable promotion; дизайн-проект сам не является разрешением публикации.

## 8. Протокол каждого патча и требования к доставке

Для каждого этапа используется текущий контракт RouterForge:

`PRECHECK → GATES → ACTION → LIVE → VERIFY → RESULT`

**PRECHECK:** ZIP SHA256, точная база `dev`, исходные blob SHA, инструменты git/gh и разрешённые пути, снимки Main/Stable/Beta releases.

**GATES:** все операции до коммита, whitelist и хеши payload, проверка формата и сборки; любой FAIL останавливает мутацию. Никаких «пустых PASS» после ошибки.

**ACTION:** один коммит в `dev` с чётким scope, push только `dev` после повторной проверки remote head. Нет правок сессий SSH/роутеров/VPS.

**LIVE:** получить **точный** Run ID от Actions API по отправленному SHA; выполнить `gh run watch <exact-id> --exit-status`; при FAIL сразу показать провалившийся job/log.

**VERIFY:** exact head SHA и фактический статус рабочих jobs; Main и текущие release assets не менялись. Отдельно фиксировать, что Dev CI мог обновить rolling Dev — это разрешённое автоматическое следствие push в `dev`.

**RESULT:** единый итог PASS/FAIL, SHA, CI Run ID, затронутые файлы, проверки и следующий этап. Если push успел пройти, не применять бездумный rollback по месту; прежде сверить remote state.

## 9. Границы безопасности и откат

- **Никакого изменения системной логики:** nftables/iptables/NFQWS/DNS/CrowdSec/Odin/Port Access/OPKG и API вне этого UI-проекта.
- **Никакого переизобретения схем:** брать реальные интерфейсные компоненты из кодовой базы, а не делать универсальный rewrite.
- **Без подмены статусных данных:** «зелёный» только при корректном состоянии и источнике.
- **Отсутствие автопубликации Beta/Stable:** CI rolling Dev допустим, full_release — запрещён до отдельного разрешения.
- **Изолированный hardware test:** DSTest ARM64 только после явного шага проверки, production router untouched.
- **Откат:** revert конкретного UI-коммита в `dev` с новой CI-проверкой; непроверенные патчи не заливать на действующие устройства.

## 10. Приёмка и управление scope

**Критерий завершения всей программы:** на каждом собственном экране одна дизайн-система, отсутствие визуальных конфликтов при RU/EN, dark/light и разных ширинах, доступность и сохранённый полный функционал. Приоритет: функциональная целостность → понятность → согласованность → декоративные детали.

**Уровни готовности:** `PENDING` — не начато; `READY` — пакет собран, но CI не выполнялся; `CI PASS` — опубликован dev код; `HARDWARE PASS` — проверен на разрешённом роутере; `RELEASE READY` — допускается обсуждение отдельной публикации.

**Порядок решений:** первый пакет P0 выполняет только Foundation. Затем P1 «Настройки» как показательный шаблон; только после его визуальной приёмки переносим паттерны на остальные страницы. Это исключает серию крупных коммитов с разом сломанной навигацией.

## 11. Ближайшие действия

5. Перейти к Core страницам и затем менеджерам по матрице выше.
