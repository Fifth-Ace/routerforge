# E03 — pinned native list references and installation observer

- `list-ref` supports `dns.<managed-list-id>@<64-lowercase-hex-sha256>` or `nfqws.<filename.list>@<64-lowercase-hex-sha256>`. Existing unqualified values are preserved but cannot be resolved. Plain qualified references can be inspected but cannot be inserted until pinned. DNS names are bounded to 40 chars, NFQWS to 80, no traversal. No file paths or URLs.
- Enter the exact ID/name in the policy group editor, click Check revision and explicitly Pin in draft. Save the catalogue through the existing Preview/Save controls. `GET /api/platform/foundation/native-reference?ref=...` returns metadata/count/pin/status only. `GET .../native-references` returns direct and transitive usage in saved groups. The existing catalogue validation rejects dangling group/device links; the UI warns before deleting referenced items.
- DNS uses the existing Unix socket `/v1/config` saved configuration, not the applied configuration. Fingerprint covers selected list policy metadata and normalized domain membership, not unrelated upstream config. NFQWS uses the existing `/v1/list?name=...` endpoint, checks the exact returned content SHA and size; only ordinary domain lines and `#` comments accepted. Non-domain syntax, wildcard/IP/CIDR, backup names, oversized data, unavailable modules, stale pins and more than eight distinct native sources per projection fail closed. Limits: 2 MiB JSON payload, 4096 labels, 8 seconds per request. No external HTTP, download or DNS/probe, no native list writes.
- Membership is not routing semantics. Native list rules and NFQWS exclusions are not transplanted as rules. Consumers resolve the saved pin twice (preview and explicit insertion), then fill the existing local draft only; all native validation, confirmation, save and apply still belong to the respective module. A saved catalogue reference is durable; **a permanent binding from a consumer's applied rules to a catalogue object is still open**. Deleting a native file elsewhere makes references unavailable, not silently replaced. No cross-module deletion interception or background polling. Updating native content requires an explicit re-pin; no automatic writes. Restored catalogue revisions preserve pins. UI uses exact IDs/names, not automatic enumeration of all native lists.
- Core initializes `observer-v1.id` in the existing `/opt/etc/routerforge` directory on startup (only new installation metadata). Exclusive atomic creation, UUIDv4, 0600 temp file, no overwrite of invalid/symlink/nonregular identity. Events and local metrics use the same persistent installation ID; exports fail closed if identity unavailable. Do not copy this ID when cloning an installation; device/connection identity remains unbound. Reinstallation without retained data is a new observer. No modification of security.json, KeeneticOS, Entware service or runtime rules.
- A successful catalogue save emits the existing normalized `policy.catalog.saved`, and `policy.catalog.references.changed` when the saved reference graph changes. No event on a GET/preview; no invented notification of native file changes or applied-rule state. Hardware verification and cross-product acceptance remain pending.
